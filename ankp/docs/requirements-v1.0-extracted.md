1. 文書概要
1.1 目的
本書は、AIネイティブ開発人材を育成する体系学習、業界標準ナレッジの蓄積、最新AIニュースの継続配信、実プロジェクトの診断を統合した公開型プラットフォームの要件を定義する。
利用者が本アプリ内で主要知識を習得し、必要に応じて一次情報へ遷移できる構成とする。教材やニュースはAIが生成を支援するが、公開内容の根拠、日付、出典、評価、修正履歴を追跡可能にし、未確認情報を断定しない。
1.2 背景と解決する課題
AI開発がコード生成の使い方に偏り、モデル選択、評価、RAG、エージェント権限、監視、フォールバック、既存API統合まで体系的に学べる場が少ない。
AI業界の情報量が多く、「バズっている情報」と「数年間使える業界標準」が混同されやすい。
生成AIが日々教材を作れる一方、根拠のない説明、日付の混在、曖昧なクイズ、重複、著作権上の問題が発生しうる。
学習成果がクイズ正答率だけで評価され、設計レビュー、リスク発見、運用判断に転移したかを測りにくい。
実プロジェクトで、AIが読む情報、AIのID、承認操作、評価履歴、モデル切替の責任分界が曖昧になりやすい。
1.3 本システムの位置付け
ニュースアプリでも静的教材でもない
本システムは「AI開発標準ナレッジ」「Daily AI」「Standard Watch」「実践学習」「プロジェクト診断」を結合した、継続更新型のAI開発人材育成基盤である。

公開コンテンツは、収集元の利用条件、引用、著作権、robots.txt等を確認した範囲で扱う。
AIの出力は確率的であるため、ルール・評価データ・人間承認・訂正フローを組み合わせる。
標準ナレッジの更新頻度は「日々」ではなく、業界での定着を確認した時点とする。日次処理は候補検出までを基本とする。
Daily AIは最新性を重視するが、話題性、信頼性、実務影響、成熟度を別々に表示する。

2.4 重要な設計原則
標準と速報を分ける：長期知識を日々の話題で上書きしない。
根拠先行：教材を書く前に、情報源をClaimへ分解する。
AIと人間の責任分界：AIは候補生成・検証支援、人間は高リスク公開と標準昇格を承認する。
学習内完結：主要な理解はアプリ内で完結し、外部リンクは検証・深掘り用とする。
判断を学ぶ：知識量ではなく、見抜く・設計する・運用する能力を伸ばす。
モデル非依存：生成・検証・検索をModel Gateway越しに扱い、評価を通じて切替可能にする。

4.5 検索とAIアシスタント
検索はキーワード、セマンティック検索、カテゴリ、期間、成熟度、出典信頼度、対象ロールを組み合わせる。AIアシスタントは検索結果と登録済みClaimだけを根拠に回答し、確認済み、推論、提案、未確認を区別する。
回答不能を許容する
根拠が不足する場合は「確認できない」と回答し、最も近いナレッジ、検索条件、一次情報を案内する。回答を埋めるための推測は禁止する。

5.4 標準昇格・降格条件
複数の独立した一次情報または標準・ベンダーで共通する概念であること。
一定期間の採用継続、実装事例、運用上の再現性が確認できること。
特定製品のマーケティング用語ではなく、一般化可能な課題・解決パターンとして説明できること。
既存標準ナレッジとの関係、代替、トレードオフ、適用条件が整理されていること。
昇格・降格はAIの提案だけで決定せず、コンテンツ責任者の承認と理由記録を必須とする。

5.6 標準ナレッジの更新処理
日次で情報源とDaily AIを監視し、既存ナレッジへの影響候補を作成する。
AIが「影響なし／補足候補／成熟度変更候補／新規候補／非推奨候補」を分類する。
コンテンツ責任者が根拠、採用範囲、実務影響をレビューする。
版を作成し、既存教材・クイズ・診断ルールへの影響分析を行う。
承認後に公開し、変更通知と旧版へのリンクを残す。
6. Daily AI要件
6.1 目的
Daily AIは、その時点で注目されるAI業界ニュース、開発ツール、モデル、研究、規制、企業動向、セキュリティ事案を毎日整理する。速報性だけでなく、事実確認、話題性、実務影響、成熟度、関連標準ナレッジを提示する。
6.2 対象ニュース
新モデル・API・開発ツール・クラウド機能の発表と重要な変更。
AI企業の提携、投資、買収、組織・提供戦略の変化。
研究成果、ベンチマーク、オープンソース、開発者コミュニティの注目技術。
規制、判決、ガイドライン、標準、社会的議論。
セキュリティインシデント、脆弱性、誤用、運用上の教訓。
AIがソフトウェア開発、仕事、組織運営へ与える変化。

6.5 日次生成・配信
設定された情報源を少なくとも1日1回収集し、重複クラスタリング、差分、日付、出典を確認する。
毎日、重要ニュース、バズ、開発者向け、規制・社会、研究等の配信枠を構成可能にする。
ニュースから短いクイズを生成する。ただし正解はClaimで直接裏付けられる内容に限定する。
高リスク、係争中、単一情報源、一次情報未確認の内容は自動公開せず、レビュー待ちとする。
誤報や訂正を検知した場合、公開ページに訂正を表示し、関連クイズを停止・再評価する。
6.6 Daily AIと標準ナレッジの接続
Standard Watch
Daily AIの個別ニュースを直接「標準」にしない。複数ニュース、一次情報、採用事例、時間経過を束ねてStandard Watch候補を形成し、成熟度を追跡する。

10.4 版管理・再現性

10.5 保存・削除方針
具体的な保持期間は法務・セキュリティレビューで確定する。少なくとも、公開証跡、訂正、承認、標準化判断は長期保持対象とし、ユーザー学習データは利用目的、同意、削除要求に基づいて管理する。Sourceの全文保存が許可されない場合は、必要最小限の抜粋、メタデータ、ハッシュ、URLを保持する。

AIからのツール入力は構造化スキーマで検証し、自由文を直接危険なAPIへ渡さない。

付録B. 用語集
用語
定義
AI Native Development
AIを機能として追加するだけでなく、モデル、データ、評価、権限、監視、障害対応を前提に開発・運用する考え方。
Claim
出典によって検証できる単一の事実・主張。教材や問題の根拠単位。
Grounding
外部情報や登録知識に回答を根拠付けること。
RAG
検索した外部情報を生成処理へ与え、回答を根拠付ける構成。
Agent
目標に基づきモデル、ツール、状態、ルールを組み合わせて処理する実行主体。
Tool Calling
モデルが構造化された引数で外部機能を呼び出す仕組み。
MCP
AIアプリケーションとデータ・ツールを接続するためのプロトコル。採用しても権限・同意・監査は別途必要。
Evaluation / Evals
モデル・Prompt・RAG・ツール・コンテンツの品質を再現可能に測る仕組み。
Golden Dataset
期待結果、評価基準、代表・境界事例を持つ固定評価データ。
LLM-as-a-Judge
モデルを評価者として利用する方法。ルール・人間評価・校正と組み合わせる。
Observability
モデル、検索、ツール、コスト、遅延、エラー、承認を追跡・分析できる状態。
Model Gateway
複数モデルへの接続、ルーティング、監査、予算、フォールバックを抽象化する層。
Human-in-the-Loop
人間が承認、判断、修正、監督へ関与する設計。
Standard Watch
Daily AIの話題が業界標準へ定着する過程を観測・評価する領域。
Source Snapshot
特定時点に取得した情報源の内容・メタデータ・ハッシュ。
Provenance
コンテンツの由来、生成過程、根拠、変更、承認を追跡できる情報。
Prompt Injection
外部入力に含まれる命令により、AIが意図しない情報開示やツール実行を行う攻撃・リスク。
Fallback
障害や品質未達時に再試行、代替モデル、固定応答、人間引継ぎ等へ切り替えること。
